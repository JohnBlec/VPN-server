# Связь VPN-сервера с сайтом

Публичное развёртывание сайта на Ubuntu 22.04 с доменом aegis-adm.ru:
[production-инструкция](https://github.com/JohnBlec/VPN_Web-app/blob/main/docs/production-ubuntu.md).
Она также описывает подключение нескольких VPN VPS к одному сайту.

## Текущий статус

Добавлен закрытый `GET /v1/traffic?after=CURSOR`: накопленные дневные итоги и время
рукопожатия. Агент собирает их раз в минуту, хранит в `data/traffic.sqlite3` и сохраняет
после отзыва профилей. Для отображения обновите сайт и все VPN-агенты по
[инструкции статистики](https://github.com/JohnBlec/VPN_Web-app/blob/main/docs/traffic.md).
Скорость не собирается. Сохраняйте весь `data` при обновлении и резервном копировании.

API агента и адаптер Django реализованы. Клиентский кабинет поддерживает создание,
скачивание и отзыв профилей; worker синхронизирует подписки и блокировки.
Администратор сайта вручную назначает клиенту разрешённые VPN-серверы и выбирает
общий лимит профилей или отдельные лимиты для каждого сервера. Клиент выбирает
назначенный сервер при создании профиля. Отзыв назначения запрещает скачивание
сразу и отключает профили при следующей успешной сверке worker.
Необходимо зарегистрировать реальный агент и запустить worker по
[инструкции сайта](https://github.com/JohnBlec/VPN_Web-app/blob/main/docs/vpn-integration.md).

## Кто чем управляет

| Компонент | Ответственность |
|---|---|
| Django + PostgreSQL | Аккаунты, роли, принадлежность устройств, подписки, лимиты, история операций |
| Фоновый worker сайта | Применение операций к VPN, повтор после ошибки, сверка фактического состояния |
| VPN API | Ключи и IP устройства, добавление/отключение peer, выдача `.conf` |
| AmneziaWG | Передача VPN-трафика |

API имеет один машинный токен администратора. **Клиенты сайта не должны получать его
или обращаться к API напрямую.** Все проверки владельца и подписки выполняет Django.

## Защищённый транспорт

API опубликован на **127.0.0.1:8787 VPN-хоста**, а не на его публичном IP.
Не меняйте binding на `0.0.0.0` для удобства. Для сайта на другом сервере используйте SSH
с отдельным ключом и ограниченным пользователем; HTTP находится внутри шифрованного туннеля.

Для production используйте [помощник сайта add-vpn.sh](https://github.com/JohnBlec/VPN_Web-app/blob/main/docs/add-vpn.md):
он создаёт постоянный туннель и выполняет настройку пользователя сам. Ниже — ручной
вариант для диагностики или локальной проверки; не создавайте второй туннель
к уже подключённому физическому агенту.

**Агент выделяется одному сайту.** Worker сайта отключает все неизвестные его базе
профили, включая созданные вручную CLI или `first-phone`. Проверку первого подключения
выполните до включения worker; после интеграции создавайте устройства через сайт.

На VPN-хосте создайте пользователя `aegis-agent` без пароля и добавьте публичный ключ
сервера сайта в его `~/.ssh/authorized_keys`:

```bash
sudo adduser --disabled-password --gecos '' aegis-agent
sudo install -d -m 700 -o aegis-agent -g aegis-agent /home/aegis-agent/.ssh
sudo touch /home/aegis-agent/.ssh/authorized_keys
sudo chown aegis-agent:aegis-agent /home/aegis-agent/.ssh/authorized_keys
sudo chmod 600 /home/aegis-agent/.ssh/authorized_keys
sudoedit /home/aegis-agent/.ssh/authorized_keys
```

В файл вставьте строку ниже, заменив `ssh-ed25519 YOUR_SITE_PUBLIC_KEY` содержимым
публичного `.pub`-файла, созданного на сервере сайта:

```text
restrict,port-forwarding,permitopen="127.0.0.1:8787",command="/bin/false" ssh-ed25519 YOUR_SITE_PUBLIC_KEY
```

В отдельном файле `/etc/ssh/sshd_config.d/aegis-agent.conf`:

```text
Match User aegis-agent
    PasswordAuthentication no
    AuthenticationMethods publickey
    AllowTcpForwarding local
    PermitOpen 127.0.0.1:8787
    AllowAgentForwarding no
    X11Forwarding no
    PermitTTY no
Match all
```

Пользователь не состоит в `docker` и не имеет `sudo`. Команда `/bin/false` блокирует
shell/команды, но `ssh -N` не открывает командный сеанс и может пробросить разрешённый порт.
Каталог `.ssh` должен иметь режим 700, `authorized_keys` — 600, владелец — `aegis-agent`.
Проверяйте `sshd -t` перед `systemctl reload ssh`; существующий SSH-сеанс сохраняйте
открытым до проверки нового соединения. Учитывайте существующие `AllowUsers`/Match-правила.
Источник: [OpenSSH authorized_keys](https://man.openbsd.org/sshd.8#AUTHORIZED_KEYS_FILE_FORMAT).

```bash
sudo /usr/sbin/sshd -t && sudo systemctl reload ssh
```

Примеры используют стандартный `AGENT_PORT=8787`. Если он изменён в `.env` VPN,
согласованно замените порт назначения в PermitOpen, authorized_keys и SSH-туннеле.

Тест с хоста сайта:

```bash
ssh -NT -o ExitOnForwardFailure=yes -o StrictHostKeyChecking=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -i /secure/path/vpn_ssh_key \
  -L 127.0.0.1:18787:127.0.0.1:8787 aegis-agent@VPN_PUBLIC_IP
```

Заранее добавьте **проверенный** ключ VPN-хоста в `known_hosts`. Сравните его fingerprint
с `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` в доверенном сеансе на VPS;
один `ssh-keyscan` без сверки не проверяет подлинность. Не используйте `StrictHostKeyChecking=no`.

В другом терминале сайта `curl --fail http://127.0.0.1:18787/healthz` должен вернуть `ready=true`.
Этот адрес доступен хосту. Внутри Docker `127.0.0.1` относится к самому контейнеру.
Для Docker backend предусмотрен [Compose-туннель](../integration/README.md), который
разделяет его сетевое пространство. Он работает и при размещении сайта и VPN на одном VPS.

## API v1

Каждый запрос к `/v1/*`: `Authorization: Bearer <содержимое secrets/agent_token>`.
Токен передаётся заголовком, не query string. JSON-тела ограничены 4096 байт.
`/healthz` без токена сообщает только локальную готовность.

| Метод и путь | Тело / результат |
|---|---|
| `GET /healthz` | `200 {"ready":true}` или `503` |
| `GET /v1/peers` | Список без приватных ключей; `revision`, `applied_revision` |
| `GET /v1/traffic?after=CURSOR` | Накопленные дневные итоги и данные активности; `source`, `revision`, `next_cursor`, `more`, `sampled_at`, `peers`, `days`, `error` |
| `PUT /v1/peers/{device_uuid}` | `{"name":"Телефон"}`; создаёт устройство или возвращает существующее |
| `GET /v1/peers/{device_uuid}` | ID, имя, публичный ключ, IPv4/IPv6, enabled, created_at |
| `PATCH /v1/peers/{device_uuid}` | `{"enabled":false}` / `true`; применяет отключение/включение |
| `DELETE /v1/peers/{device_uuid}` | Окончательно отзывает устройство; повтор безопасен |
| `GET /v1/peers/{device_uuid}/config` | Текст `.conf`, содержит секреты, `Cache-Control: no-store` |

Ответы: `400` неверные данные, `401` токен, `403` отключённый peer, `404` отсутствует,
`409` конфликт имени/ID или заполнена подсеть, `503` состояние VPN не применено.
Не пытайтесь распарсить тело `.conf` как JSON. API не отдаёт произвольный путь с диска
и не выполняет переданные пользователем команды.

Курсор статистики — целое число от 0 до `2^63-1`. Первое чтение выполняется с
`after=0`; следующие — с `after=next_cursor`. При `more=true` прочитайте следующую
страницу (до 250 дневных строк). Значения накопленные: повтор страницы не должен
прибавлять тот же расход второй раз. При новом `source` или откате `revision`
сбросьте курсор. Ответ `503` означает, что хранилище статистики не инициализировано;
поле `error` в успешном ответе сообщает об ошибке последнего измерения.

## Реализованный контракт сайта

1. Используются VPNServer и VPNDevice. Устройство связано с Customer, имеет UUID, выбранный сервер,
   желаемый статус, время последней синхронизации и текст последней ошибки.
2. URL хранится в VPNServer, токен — в отдельном файле backend. Не добавлять
   токен в `NEXT_PUBLIC_*`, localStorage, фронтенд или ответы API сайта.
3. При создании устройства проверить владельца, подписку и лимит **в транзакции**,
   зарезервировать UUID и поставить задачу worker. Вызвать PUT с этим UUID.
4. Подтверждать выдачу после успешного ответа. При таймауте или `503` повторять тот же ID;
   смена ID при каждом retry создаст лишние устройства.
5. Для скачивания каждый раз проверять клиента/подписку и проксировать `/config` через
   backend с `no-store` и Content-Disposition. Сайт также формирует QR-код из текста
   `.conf` в браузере, без передачи конфигурации сторонним сервисам.
6. Истечение подписки, блокировка и архивирование должны ставить PATCH enabled=false
   для всех устройств клиента. Продление — enabled=true, если нет ручной блокировки.
7. Периодическая сверка сравнивает peers с базой сайта. Недоступность сервера не означает
   успешное отключение: хранить `pending/error`, повторять и показывать администратору.
8. Административные операции журналировать без приватных ключей и конфигураций.
9. При восстановлении бэкапа VPN сначала сверять с актуальной базой подписок: старый бэкап
   может снова включить отозванные профили.

VPN-контроллер сохраняет желаемое состояние до вызова `awg syncconf`. Если применение
сорвалось, файл остаётся для повтора; reconciler повторяет каждые 15 секунд. Это **локальная
сверка контейнера**, она не заменяет проверку подписок сайта.

Время подписи/оплаты и токены пользователей передавать VPN-серверу не требуется.
Пиры не ограничивают пользователя по физическому устройству: скопированный профиль может
использоваться на другом устройстве. Лимит сайта относится к количеству выданных профилей.
